## `checkpoint_accuracies.csv`

`analysis/checkpoint_selection.py` consumes this to produce Table S8. It exists because
Table S8 is an analysis of 290 checkpoint files totalling ~26 GB, of which only the accuracy
in each file *name* is needed — a few kilobytes.

Header row present. One row per retained `.ckpt`.

| Column | Meaning |
|---|---|
| `model` | `model_type` from the run's own `dump_config` JSON (`efficientnet_b0`, `fastvit`, `htsat`, `mobilenetv3`, `resnet18`, `tinyvit`) |
| `fold` | `esc_fold` from the same JSON, i.e. the held-out fold, 0–4 |
| `checkpoint` | the checkpoint file name, verbatim |
| `accuracy` | held-out accuracy parsed out of that file name, 3 decimals |
| `experiment` | run directory name, e.g. `tinyvit_3class_fold0` |
| `task` | `3class`, `2class`, `ablation:<name>` or `class_weight_sweep:<weights>` |
| `version` | Lightning `version_N` under `checkpoint/lightning_logs/` |
| `epoch` | epoch index parsed out of the file name |
| `duplicate_name` | 1 if the name carried Lightning's `-v1` collision suffix |
| `is_primary_run` | 1 for the run that produced the published numbers (see below) |
| `model_label` | display name used in the paper (`MobileNetV3-S`, `HTS-AT`, …) |

**Provenance.** Generated by listing
`data/results/*/checkpoint/lightning_logs/version_*/checkpoints/*.ckpt` and matching each
name against `^l-epoch=(\d+)-acc=(\d\.\d{3})(-v\d+)?\.ckpt$` — the template
`l-{epoch:d}-{acc:.3f}` that `ModelCheckpoint` was configured with. No checkpoint was opened.
`model`/`fold`/`task` come from each run's `<experiment>.json` config dump rather than from
the directory name. The 61 run directories are not redistributed, so this CSV cannot be
regenerated from the repository; it is terminal evidence.

**Why there are four checkpoints per run, and why there is no `monitor` column.** Training
attached *two* `ModelCheckpoint` callbacks, `monitor="acc"` (mode max) and `monitor="loss"`
(mode min), each with `save_top_k = 2`, and **both** used the same file-name template
`l-{epoch:d}-{acc:.3f}`. Each run therefore retains four files — the two best by held-out
accuracy plus the two best by validation loss, all four named by their accuracy — and which
callback wrote a given file is not recoverable from its name. Table S8's "four checkpoints
each run retains" is exactly this set. The `-v1` suffix appears when both callbacks selected
the same epoch and the second write collided with the first.

**`is_primary_run`.** Four experiments contain checkpoints from more than one Lightning
version, so a rule is needed:

| Experiment | versions with checkpoints | primary | why |
|---|---|---|---|
| `mobilenetv3_3class_fold0` | 0–9 | 9 | versions 0–8 stop at epoch ≤ 8 (crashed launches); version 9 is the full 150-epoch run |
| `tinyvit_3class_fold0` | 0, 1 | 1 | version 0 stops at epoch 2; version 1 reaches epoch 146 and its `l-epoch=119-acc=0.882.ckpt` is the checkpoint `qat_results.log` loads |
| `tinyvit_3class_fold4` | 0, 1 | 1 | version 0 stops at epoch 36; version 1 reaches epoch 149 |
| `tinyvit_binary_fold0` | 0, 1 | 1 | both completed; version 1 finished at 21:44 and `tinyvit_binary_fold0.data.csv` was written at 21:46, so version 1 is the run that was tested |

Rule as implemented: the version whose highest epoch is greatest, ties broken by the higher
version number. All other 57 experiments have a single version with checkpoints.

**Independent check.** Restricting to `task = 3class`, `is_primary_run = 1` and the 30
`*_fold{0..4}` runs, then averaging over the five folds, reproduces Table S8:

| Model | Peak (recomputed / published) | Mean of retained (recomputed / published) | Difference pp (recomputed / published) |
|---|---|---|---|
| MobileNetV3-S | .8572 / .857 | .8498 / .850 | 0.73 / 0.73 |
| FastViT | .8580 / .858 | .8501 / .850 | 0.79 / 0.79 |
| EfficientNet-B0 | .8558 / .856 | .8495 / .849 | 0.63 / 0.63 |
| TinyViT | .8632 / .863 | .8549 / .855 | **0.82 / 0.78** |
| ResNet-18 | .8470 / .847 | .8432 / .843 | 0.38 / 0.38 |
| HTS-AT | .8040 / .804 | .7895 / .790 | 1.45 / 1.44 |

Every peak and mean matches to the printed precision. The TinyViT difference recomputes as
0.82 pp against a printed 0.78 pp; note that .863 − .855 = 0.8 pp, so the printed 0.78 is also
not consistent with the same row's own peak and mean. The supplement's summary range
recomputes as 0.38–1.45 pp, mean 0.80 pp, against a printed 0.38–1.44 pp, mean 0.79 pp. See
`docs/errata.md`.

## `benchmarks/`

Both files come from `benchmark_orangepi.py` (now `deployment/edge/benchmark.py`) on an
Orange Pi Zero 2 W (Allwinner H618, Cortex-A53 ×4 @ 1.5 GHz, 4 GB), ONNX Runtime 1.24.2,
`intra_op_num_threads = 4`, `ORT_ENABLE_ALL`, CPU execution provider, 20 timed runs after 3
warmups, on the same `deployment/edge/bench_input.npy`
(sha256 `f8a7c2d832b305de234c16f31c66e476065574915f1204d98966c78f17235d05`).

`benchmark_2026-02_4arch.json` is shipped **byte-for-byte** as the script wrote it: it is the
primary record for Table 4 and is deliberately not reformatted.

`benchmark_2026-07_6arch.json` holds only the four rows of the July session
(MobileNetV3-S and ResNet-18, FP32 and static INT8) — the rows that complete the
six-architecture set used by `analysis/table4_ondevice.py`. In the working tree these had been
hand-appended to a copy of the February file, out of the script's `sorted()` order and under
the February timestamp; the two sessions are kept separate here so that no single file implies
one measurement session. The `timestamp_provenance` field states exactly how far the date can
be pinned down (the on-device run was never independently timestamped).

**Table 4 verified row by row against `benchmark_2026-02_4arch.json`: all seven rows and all
four numeric columns match**, at the rounding printed in the paper.

| Table 4 row | Latency ms | Size MB | Peak RSS MB | Throughput |
|---|---|---|---|---|
| EfficientNet-B0 INT8 static | 210.13 → 210 | 4.33 → 4.3 | 101.9 → 102 | 4.759 → 4.76 |
| EfficientNet-B0 FP32 | 456.53 → 456 | 15.3 | 132.9 → 133 | 2.19 |
| FastViT FP32 | 510.47 → 511 | 24.95 → 24.9 | 109.7 → 110 | 1.959 → 1.96 |
| FastViT INT8 static | 666.39 → 666 | 3.67 → 3.7 | 113.5 → 114 | 1.501 → 1.50 |
| TinyViT INT8 static | 1294.21 → 1,294 | 6.42 → 6.4 | 195.3 → 195 | 0.773 → 0.77 |
| HTS-AT FP32 | 1392.65 → 1,393 | 109.44 → 109.4 | 248.7 → 249 | 0.718 → 0.72 |
| TinyViT FP32 | 1435.98 → 1,436 | 20.1 | 195.3 → 195 | 0.696 → 0.70 |

Two notes on figures that appear in Sec. 3.5's prose rather than in the table itself:

- The FastViT FP32 size of 24.95 MiB is the sum of `model_fp32.onnx` (12.51 MiB) and a
  sibling `model_fp32.onnx.data` (12.44 MiB), because the benchmark adds a `.data` file to the
  model size when one exists. That external-data file is a stale artifact: the `.onnx` has no
  external initializers and loads and runs on its own, so the deployable FastViT FP32 graph is
  12.5 MB. The released asset contains only the 12.5 MB file.
- Dynamic-INT8 average latencies in the file are EfficientNet-B0 1516.45 ms, FastViT
  1533.33 ms, TinyViT 2039.75 ms, HTS-AT 1089.29 ms. Sec. 3.5(1) quotes 1,517 ms for
  EfficientNet-B0. Relative to FP32 these are 3.32×, 3.00×, 1.42× and 0.78×; relative to each
  model's static-INT8 build they are 7.22×, 2.30× and 1.58×, so the table footnote's
  "2–7× slower" range corresponds to the static-INT8 denominator. See `docs/errata.md`.

## `logs/`

Three run logs, force-added past the `*.log` ignore rule because they are the only surviving
evidence for three claims in Sec. 3.5. Absolute paths from the authoring machine were
replaced in place by `<repo>/` and `<venv>/`; this is a pure substring substitution that
changes no line's index, so the line references below and in `docs/` are the line numbers of
the shipped files.

- **`static_fp16.log`** — FP16 agreement with FP32 is 100.0 % (739/739) at line 179 and
  99.9 % (738/739) at line 369. Static-INT8 accuracy is 0.7876 at lines 95 and 457; 0.7876 is
  582/739, the *Absent* prior of the fold-0 evaluation set exactly, i.e. the signature of a
  constant classifier.
- **`int8_quantization.log`** — segment-level dynamic-INT8 validation, and at lines
  516/522/528/534 the four checkpoints that were exported to ONNX
  (`htsat_3class`, `efficientnet_b0_3class`, `fastvit_3class`, `tinyvit_3class`, matching the
  four single-split files in `predictions/`). It also preserves ONNX Runtime's own
  "Please consider to run pre-processing before quantization" warning.
- **`qat_results.log`** — the QAT run. Lines 40 and 90 read, verbatim and identically:

  ```
      Convert failed (cannot pickle 'module' object), using fake-quant metrics instead
  ```

  `torch.ao.quantization.convert` therefore never produced a quantized model, and the
  reported "QAT INT8 Challenge Score" (TinyViT 0.3184 at line 50, EfficientNet-B0 0.3555 at
  line 100) is the last **fake-quantized** evaluation, not a measurement of an INT8 model.
  The same log records the fine-tuning trajectory diverging well below the three-class chance
  floor (TinyViT accuracy 0.8836 → 0.5767 → 0.2487 → 0.0899 at lines 21 and 25–29). Read
  those numbers as "fake-quantized, eager mode, unfused, front end quantized, training
  diverged, `convert` failed"; `docs/errata.md` and `docs/quantization.md` state what is and
  is not established.
